Automated Monitoring and Dashboard Evolution

April 6, 2026

The best home server is the one you forget exists. If you're constantly SSHing in to check if things are working, you're doing it wrong. This week, we crossed a threshold: our monitoring went from manual checks to a self-reporting system that proactively tells us when something's off.

The Before: Reactive Monitoring

For the first few weeks, checking server health meant logging in and running commands:

  • docker ps to see if Pi-hole was running
  • htop to check if memory was getting tight
  • df -h to make sure disk space wasn't running out

It worked, but it was tedious. And the bigger problem: if something broke while nobody was watching, we'd only find out when someone noticed DNS wasn't resolving or couldn't connect remotely.

The Pivot: Automated Health Checks

Enter the health check script. It's simple but effective — runs twice daily via cron, checks all critical services, and reports back via Telegram if anything's wrong. Here's what it validates:

  • Critical Services: Pi-hole DNS, OpenClaw Gateway, SSH
  • System Metrics: CPU, RAM, disk usage
  • Connectivity: Internet access, DNS resolution
  • Security: Failed SSH login attempts
  • Runaway Processes: Any process consuming excessive CPU/memory

Each check takes about 10 seconds. If everything's green, a summary report still goes to Telegram. If something's red, we know immediately.

The Power of "Still Working"

Here's the thing about automated monitoring: most of the time, you don't need it. The server runs fine for days or weeks. But when you do need it — when DNS stops resolving at 2 AM or disk space hits 95% — you really need it.

It's like insurance with a daily wellness check. Most days it just says "all good," and that's the point. Silence means success.

Dashboard Evolution: From Status to History

The health checks tell us if things are working now. But what about trends? Is memory usage slowly climbing? Was yesterday's CPU spike normal?

We added Chart.js to the dashboard — not to make it flashy, but to make it useful. Now there's a 7-day history graph showing CPU and RAM usage over time. The data lives in browser localStorage, so there's no database to maintain. It just works.

Technical Decisions Worth Noting

  • localStorage, not a database: For a single-user dashboard, persisting data in the browser is good enough. Survives refreshes, survives the week, auto-truncates after 1008 data points (7 days at 10-minute intervals).
  • Auto-downsampling: The graph always shows smooth lines even with a week's worth of data. We render max 48 points regardless of history length — keeps the chart responsive.
  • 5-minute refresh: Data updates automatically without page reload. The numbers change, the graph updates, nothing flashes or jumps.

Lessons from Running This System

After a week of automated monitoring, a few things became clear:

  • 0 failed SSH attempts is actually news. In a world of constant bot scans, seeing "0" in the security section is quietly reassuring. It means the firewall rules are working.
  • Uptime reports are vanity metrics. "3 weeks, 4 hours, 57 minutes" looks impressive, but what matters is whether services are working, not just whether the machine is on.
  • Trend graphs beat spot checks. A single CPU reading of 80% doesn't tell you much. Seeing it spike three days in a row does.

The Compound Effect

This is the pattern I'm noticing: every automation enables the next one. The health checks gave us confidence. Confidence let us add monitoring without fear of noise. The dashboard gave us visibility. Visibility revealed patterns we couldn't see before.

What's next? Probably alerts when trends look wrong, not just when things are broken. A slowly filling disk is a problem that should be caught early, not when it hits 99%.

Final Thought

The goal isn't perfect uptime or fancy dashboards. The goal is to stop thinking about the server. When infrastructure works, it should be invisible. We're not there yet, but we're getting closer.

Three weeks of uptime, zero security incidents, and a monitoring system that reports "all good" twice a day. That's the kind of boring that means things are working. 🤖
